# Updating the data (development only)

The delivered `../index.html` works without any of these tools. Python, network access and Node are needed only to research, rebuild or retest a future release.

1. Independently check the latest released update on the official Cyberpunk website. Do not infer per-weapon numerical validity from the absence of changes in patch notes.
2. Install the optional research dependencies: `python -m pip install -r tools/requirements.txt`.
3. Run `python tools/refresh.py --cache YOUR_RESEARCH_CACHE --staging YOUR_STAGING_FOLDER`. Use separate directories; do not target this source folder. Requests use public pages, respect robots.txt and stop on challenges. By default existing cache pages are reused; use `--force` for a new snapshot. Raw source pages belong in the research cache, not in a redistributed release.
4. Review the staged `diff.json`. The collector is intentionally conservative: if upstream schemas change, access fails, or a new iconic lacks an authored effect, fix the parser or research gap rather than treating it as an empty record. The script has no access to game files and cannot certify in-game behavior.
5. Review `tools/effects.json`, manufacturer mappings, acquisition branches, the canonical inventory and source-level differences. Update acquisition for newly added items. The normalizer deliberately retains this release's verification warnings and metadata until a maintainer reviews them; it does not automatically claim support for a newer patch.
6. Review every changed weapon's source values. Do not interpolate intermediate + tiers or combine incompatible DPS or projectile conventions. Recheck promotional rewards and their present-day acquisition separately.
   Preserve `modSlots` slot IDs and published `countByTier` tables through `tools/slot_data.py`. `PowerModule` identifies a muzzle attachment, not a mod. If a new slot identifier appears, update and test the explicit mapping rather than silently treating it as a generic mod.
7. After review, replace `weapons.json` with the accepted staged dataset. Update `meta`, source dates, version warnings, `template.html`, data notes in `app.js`, documentation and count assertions in tests to reflect the new release.
8. Update image mappings with `python tools/bundle_images.py --records YOUR_RESEARCH_CACHE/g-records.json` after reviewing the source's image associations. Existing original PNG/WebP files are reused. Inspect all new artwork, compare duplicate hashes and retain source credits. Explicit alternate sources belong in `tools/image-overrides.json`. Keep `weapon-images.json` and both `assets/iconics/` and `assets/non-iconics/` with the source. The build requires one mapped image for every weapon and checks asset hashes.
9. Build with `python build.py`. Test `../index.html` directly with `file://` while offline. Run `node tests/app.test.cjs` with Playwright installed. Set `BROWSER_EXECUTABLE` to an isolated browser executable if the default headless Edge channel is unavailable. `PLAYWRIGHT_MODULE` may name an absolute installed Playwright package directory.
10. Inspect the generated desktop, tablet and phone screenshots. Regenerate the completeness report and field-gap ledger. Package the application, normalized data, original source code, attributed image assets, image manifest and validation deliverables; exclude raw third-party pages and development dependencies.
11. Run the build again after tests and documentation are finalized. It automatically refreshes `../../Share-with-friends/Night-City-Arsenal.html`, the smaller friend-facing ZIP, `release.json` and the complete source archive. Keep the friend-facing filenames stable. Run `node tests/distribution.test.cjs` to verify the standalone share file and a fresh ZIP extraction offline; neither should depend on the source folder or original installation path.

The collection pipeline and parsers were exercised on the original snapshot, and the staged normalizer was checked against its cached records. A future live refresh is not guaranteed if a source changes its markup, data schema or access policy.
